# Notes

## Shorthands
- \[A] Power of any domain
- \[E] Exhaust symbol
- \[T] Old exhaust symbol (tap)
- \[M] Might symbol
- \[S] Old might symbol (strength)
- \[C] Power of a card's domain
- \[>] Keyword associated with an ability
- **Activated Abilities** are **Game Effects** written as **Costs** followed by a ":" and then succeeded by an effect.

## Keyword templates

### 805. Accelerate
- **805.1.** Accelerate is a Unit ability.
  - **805.1.a.** Accelerate is functionally short for "As you play me, you may pay [1][C] as an additional cost. If you do, I enter ready."
    - **805.1.a.2.** If the unit has no domain, the Power portion of the Accelerate cost can be paid with [A] (a Power of any domain).

### 806. Action
- **806.1.** Action is a Permissive keyword.
  - **806.1.a.** It is present on Cards, Rune Abilities, Legend Abilities or Permanent Abilities.
  - **806.1.b.** Action grants the corresponding card or effect permission to be played or activated during Showdowns, even when it is not the Controlling player's turn.
  - **806.1.c.** Action is functionally short for the following:
    - **806.1.c.1.** On Cards: "This can be played during showdowns on any player's turn."
    - **806.1.c.2.** On Activated Abilities: "This can be activated during showdowns on any player's turn."
  - **806.1.d.** Action is formatted as "[Action]" on spells, or "[Action][>]" on abilities.

## Syntax
**Reminder Text** appears in *italics* & (*parentheses*).
- The presence, absence or exact wording has no effect on game function.

## Semantics
**Dependent Keywords** are comprised of both a **Condition** that they are short for, and an ability of som format immediately after the **Keyword** itself.
- The **Dependent Ability** is **Inactive** on the card with the **Dependent Keyword** until the **Condition** is met, when it becomes **Active**

## Card Text Hierarchy
Rule numbers point into `Riftbound Core Rules.md`.
- **Rules Text** (135) contains, in any combination:
  - **Abilities** (135.2.a, 360) — discrete units of "what a card may or must do." Kinds:
    - **Passive Ability** (363) — a standing condition/constraint/statement; no trigger, no cost.
    - **Activated Ability** (376) — `Cost ":" Effect`.
    - **Triggered Ability** (382) — `Condition "," Instruction(s)`; fires when its Condition is met.
      - **Reflexive Trigger** (386) — a Triggered Ability spawned mid-resolution by another ability/instruction, rather than printed directly.
    - **Delayed Ability** (389) — only active during a window the creating ability defines; not tied to its source staying on the board.
    - **Linked Abilities** (393) — two or more Abilities on the same printed text (or granted by the same source) that reference each other.
  - **Instructions** (135.2.b) — imperative-mood `Game Action + Complement`, found on Spells and inside Abilities. A trigger Condition is not itself an Instruction (135.2.b.6).
  - **Keywords** (135.2.c, 800) — shorthand for a longer Ability/Instruction; may carry Reminder Text.
    - **Dependent Keyword** — `Keyword [>] Text` where Text (a Dependent Ability) is Inactive until the Keyword's Condition is met (see Semantics above).
    - **Permissive Keyword** — e.g. `[Action][>]`, grants permission to the Ability/Instruction after `[>]`.
    - **Keyword-triggered Ability** — e.g. `[Deathknell]`, the keyword itself doubles as the trigger condition.
  - **Reminder Text** (135.2.d) — *(italicized, parenthetical)*; cosmetic only, never affects game function.
  - **Symbols** (135.2.e) — `[E]` exhaust, `[M]` might, `[A]` power of any domain, `[C]` power of this card's own domain, domain symbols, `[>]` keyword-to-ability link.
- **Effect Text** (136) — a second block of Abilities below Rules Text; Inactive unless the card is Attached, then appended to the host's Rules Text.
- **Might Bonus** (137) — `+N`/`-N`; modifies the Might of the card this card is Attached to.
- **Flavor Text** (138) / **Illustration** (139) — no gameplay meaning; safe for the parser to ignore.

### Interpretation Conventions
Govern how parsed text resolves; not part of the text grammar itself.
- Card text supersedes rules text (001-002); a card's own terminology, not the rules', governs how its text reads (050-051).
- Self-reference: Units/Legends say "I"/"me", Gear/Spells say "this", Battlefields say "here" (053).
- "Can't" beats "can"; "only" makes a permission exclusive (054).
- Resolve as much of an instruction as possible; ignore whatever part is impossible (055).

### Grammar Doodles
#### Hard Separation
**Rules Text** - Always the root of the AST, Defined and identified by that.

**Symbols and Keywords** - Bracket delimited. AST leaves.
- Symbols contain either a number or a single letter.
- Keywords contain a single word and a an optional single value. (Given the cost is written after the brackets.)

**Might Count/Modifier** - (+|-)? \[M\]. Always the direct parent of a Might Node if present.
- Make sure we capture the right glyph for minus here.

**Colon** - What came before was a cost, what comes after is an effect.

**—** - Ties the Node before to the node after. It might be keyword effect, like in:

	"_\[Legion\] — When you play me, play two 1 [M] Recruit unit tokens here. (Get the effect if you've played another card this turn.)_"
	
or marking a branch like in:

	"_When you attach an Equipment to me, choose one that hasn't been chosen this turn —Ready 2 runes.Channel 1 rune exhausted.Buff a friendly unit._"
	
or a cost like in:

	"_\[Empower\] — Discard 1 (Pay the cost: Empower me. Use only if not Empowered.)\[Empowered\]\[>\] I have +1 \[M\]._"
	
**\[>\]** - The ability after is tied to the keyword before. Badge should render with arrow end.

**\[>>\]** - The keyword after is tied to the keyword before. Badge after first should render with arrow indent beginning.

**Reminder Text** - Parenthesis delimited. Belongs to whatever sibling node came before it.

#### Fuzzier separation
**Effect Text** - Unknown as not present in mock data. Separate field on riot's page but not separate prop in DTO.

**Instructions** - Appr. sentence level. Begins When no text-token came before, with a capital letter, and after '.'

#### Notes
**A note on sequential symbols** - Symbols immediately following each other should be grouped. This is most commonly seen as costs, but may just be an enumeration of resources, like in \[Add\] - \[1]\[C].

**A note on hyphens** - If hyphens are connected by word-tokens on either side, the hyphen is connecting the two words rather than ending a composite node and connecting it to the next.

## Parser & Lexer Reference
Reflects `rbmlLexer.ts` and `parseFinished` in `rbmlParser.ts` as built. Each
name gets its code name plus the standard parsing/compiler term for the same
idea, since the two vocabularies describe the same things.

### Tokens (`tokenize`)
Matched in this order — one regex alternation, sticky (`/y`); order matters,
since the first alternative that matches at the cursor wins, same as ordered
choice in a PEG.

| Code name | Standard term | Matches |
|---|---|---|
| `SYMBOL` | terminal (pre-folded literal) | `[x]` or `[digits]` as one lexeme |
| `OP` | operator token | `[>]`, `[>>]` |
| `DASH` | infix operator token | `-`, `–`, `—` |
| `COLON` | infix delimiter | `:` |
| `COMMA` | list separator | `,` |
| `DOT` | clause terminator | `.` |
| `OPEN_BRACKET` / `CLOSE_BRACKET` | bracket delimiters | `[`  `]` |
| `OPEN_PAREN` / `CLOSE_PAREN` | paren delimiters | `(`  `)` |
| `WORD` | identifier | `[a-zA-Z_]+` |
| `NUMBER` | numeric literal | `\d+` |
| `SPACE` | *significant* whitespace ("layout" token) | `\s+` |
| `OTHER` | catch-all / wildcard terminal | anything else, one char |

### Grammar (`parseFinished`)
```
RulesText    = Segment*                          -- root / start symbol

Segment      = (Piece (Join Piece)*)? Terminator?
Join         = COMMA                             -- accumulate into a CommaGroup item
             | ('[' '>' ']' | Dash)               -- takeLeft(); wrap [left, Segment] as
                                                      Grouper{role:'ability'}; ends this Segment
Terminator   = DOT                                -- folds '.' onto the trailing Text; ends this Segment
             | COLON Segment                      -- takeLeft() as cost; wrap [cost, Segment]
                                                      as CostEffect; ends this Segment
             | EOF | ')' | ']'                    -- ends this Segment (and its caller's, one level up)

Piece        = SymbolRun
             | BracketExpr
             | ReminderText                       -- attaches to the previous Piece/Segment as
                                                      `.reminder` instead of becoming a Piece,
                                                      whenever one exists (else stands alone)
             | TextRun
             | Might                              -- reclaimed from a TextRun's numeric tail
                                                      plus a following [M] Symbol

SymbolRun    = Symbol+                            -- bare-adjacent Symbols fold into one SymbolGroup
Symbol       = SYMBOL | '[' NUMBER ']'

BracketExpr  = '[' WORD (SPACE NUMBER)? ']'          -> Keyword{name, param?}
                 (SPACE SymbolRun)?                  -> wraps as Grouper{role:'cost', value:[Keyword, run]}
             | '[' NUMBER ']'                        -> Symbol
             | '[' ('>' | '>>') ']'                  -- never a Piece by itself: '>' is consumed by
                                                         Join above; '>>' sets Keyword.nested on
                                                         whichever Keyword is parsed next
```

### AST node kinds (`Node`)
| Code name | Standard term | Shape |
|---|---|---|
| `RulesText` | root node / start symbol | `Node[]` |
| `Segment` | sequence node (concatenation) | `Node[]` |
| `SymbolGroup` | list node (`Symbol+`) | `Node[]` |
| `CommaGroup` | list node (comma-delimited items) | `Node[]` |
| `CostEffect` | binary expression node, COLON as the fixed operator | `[cost, effect]` |
| `Grouper` | binary expression node, generalized: one shape with an operator field (`role` + `marker`) instead of a node kind per operator | `[left, right]` |
| `Keyword` | decorated terminal (leaf plus attributes) | `{name, param?, associated?, nested?}` |
| `Symbol` | terminal / leaf | `{value}` |
| `Might` | literal-folding node (peephole merge of two already-emitted pieces) | `{amount, sign?}` |
| `Text` | terminal / leaf (raw run) | `{value}` |
| `ReminderText` | trivia node (Roslyn/LSP terminology — carried by the tree but not part of the "real" structure) | `Node[]` |
| `.reminder` (on any node) | trivia attachment | — |
| `TextGroup` | superseded by `Segment` in `parseFinished`; still produced by the old `parse` | `Node[]` |

## Design Retrospective
Where this setup is standard practice, and where it deliberately isn't.

**Lexer**
- One big regex alternation with named capture groups, run in a loop via a
  sticky (`/y`) flag — a common, pragmatic way to hand-write a lexer in a
  high-level language, since it hands DFA-construction to the regex engine
  instead of writing a character-by-character state machine by hand. Real
  systems-language compilers usually can't afford this (predictable
  performance, no reliance on a separate engine's correctness) and write
  their own scanning loop — which is exactly what bit us: the `[>]`/`sym`
  and dash bugs were bugs in *this specific regex engine's* handling of the
  pattern, not in the grammar we expressed.
- Token shape (`{name, value?}`, one union) is standard — most lexers use
  exactly this "discriminated union of kind + optional payload."
- `SPACE` being a real, kept token (not discarded or filed as trivia at the
  lexer stage) is the one genuinely unusual choice. Most grammars are
  whitespace-*insensitive*: `a+b` and `a + b` mean the same thing. Ours is
  whitespace-*sensitive* on purpose — `[Deflect][2]` (bare adjacency, no
  relation) and `[Equip] [1][R]` (space, external cost) are different parses
  of visually similar input, and the only signal that tells them apart is
  whether a `SPACE` token sits between them. That's a smaller-scale version
  of what layout-sensitive languages (Python, Haskell, YAML) do with
  indentation — whitespace as syntax, not filler.

**Parser**
- No parser generator, no combinator library — hand-written recursive
  descent. Completely typical for a grammar this size; it's also what
  production parsers for much bigger languages do by hand (V8's JS parser,
  Python's own parser, Clang), usually for error-message quality and
  performance, though ours is one guy's, for learning and directness.
- The precedence-climbing structure (`parseSegment` checking DOT, then
  COLON, then a tie, then comma, then falling through to atoms) is the
  standard technique for "a flat run of things glued by operators of
  different binding strength" — the same idea Pratt parsers use for
  arithmetic. The one place this diverges from the textbook shape: classic
  precedence climbing is usually one function *per* level, each calling the
  next-tighter one for its operand. Here all the levels live in one
  function's dispatch order instead of one call per level — more compact,
  same effect, just worth knowing it's a variant, not the textbook shape.
- Backtracking via `stream.pos = restore` (`attachExternalCost`,
  `attachReminderIfPresent`) makes this closer to a PEG (Parsing Expression
  Grammar — ordered choice, tries a rule, un-commits on failure) than a
  strict predictive LL(k) parser, which commits to a production from
  lookahead alone and never backtracks. PEGs are a normal, well-established
  choice for exactly this kind of "mostly unambiguous, a few local
  lookahead decisions" grammar.
- `Grouper{role, marker}` unifying `[>]`, dash-ties, and space-gated cost
  into one node shape (instead of one node kind per operator) mirrors a
  standard compiler instinct: prefer one generic `BinaryExpr`-style node
  parameterized by an operator field over `AddExpr`/`SubExpr`/`MulExpr` as
  separate kinds. Same reasoning applied to `CostEffect`, which could have
  been folded into `Grouper` too but was kept separate since it isn't
  keyword-specific.

**The AST itself**
- Nodes are mutated after creation (`.reminder`, `.associated`, `.nested`,
  the cost-wrapping in `attachExternalCost`) rather than built purely
  bottom-up and left immutable. That's a real divergence from the
  textbook "AST construction is a pure function of the parse" model — but
  it's also exactly how production ASTs handle trivia in practice (Roslyn's
  leading/trailing trivia, Babel's comment attachment): the "real" grammar
  produces a node, and then a separate, looser pass hangs cosmetic content
  off of it after the fact, because trivia's position in the tree doesn't
  follow the same rules as everything else.
- No separate semantic-analysis pass, no symbol table, no type checking —
  lexing and parsing produce a tree that's directly render-ready. A "real"
  language compiler pipeline is usually lex → parse → semantic analysis →
  (optimize) → codegen, as distinct stages over distinct representations.
  Collapsing straight to a render-ready tree is normal for small markup/DSL
  parsers (Markdown, template engines) where the AST *is* the deliverable,
  not an intermediate form.
- No error recovery. Malformed input throws rather than producing a partial
  tree with error nodes, unlike production language parsers (e.g.
  TypeScript's own), which must keep going through arbitrary broken user
  input to power an editor. Reasonable here since the input is a closed,
  trusted corpus rather than something a user is actively typing.
